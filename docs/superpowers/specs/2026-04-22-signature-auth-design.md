# Signature-Based Auth (Class 2: Keyed Cryptography) — Design

**Status:** design, approved for implementation planning.
**Predecessors:**
- `docs/superpowers/findings/2026-04-13-transformed-credential-problem.md` (problem analysis).
- `docs/superpowers/specs/2026-04-15-transformed-credential-fix-design.md` (Class 1 fix: Basic auth + mismatch detector, already shipped).

**Scope:** make AWS SigV4 and GitHub App JWT authentication work end-to-end through Veil. Convert the current silent-failure-plus-warning path for these two schemes into a re-sign-at-proxy path that preserves Veil's "nothing real in `.env`" invariant.

---

## Goals

1. An agent invoking `aws`, `boto3`, `@aws-sdk/*`, Terraform (SDK path), or any other AWS SigV4 client through `veil run` succeeds against real AWS. Includes long-lived IAM keys and short-lived session-tokened credentials (STS, SSO, role assumption).
2. An agent using a GitHub App (Octokit, `PyGithub`, `go-github`, direct JWT crafting) succeeds against `api.github.com` and self-hosted GitHub Enterprise Server.
3. Fail-closed guarantee: for any request where Veil recognizes the scheme AND owns the host for that scheme, either the real-signed request leaves Veil or the request is blocked at the proxy with a diagnosable error. No more `SignatureDoesNotMatch` / `InvalidAuthenticationCredential` from upstream for requests Veil could have mediated.
4. Keep signer additions bounded per scheme. No plugin registry; each scheme is a file next to the Basic decoder.

## Non-goals

- Other Class 2 schemes: HMAC webhook signing (Stripe, Twilio, Shopify), HS256 JWTs. Same design generalises; they are follow-ups.
- GitHub App installation tokens returned in response bodies (Class 3 — offline exchange). Tokens pass through Veil unmediated; agent holds a short-lived (`ghs_…`) token for its TTL.
- S3 presigned URLs and other query-string-authed AWS URLs generated by the agent. These aren't request-auth on the proxy path; they're artefacts handed off.
- AWS SigV2, AWS STS pre-signed URLs.
- Class 3 (OAuth exchange) beyond the installation-token pass-through noted above.
- Class 4 (mTLS / client certs).
- Response-body rewriting.

---

## Architecture

Two new signer functions join the injector pipeline in `internal/proxy/`, as siblings to the existing Basic decoder:

- `signAWSSigV4` — recognises `Authorization: AWS4-HMAC-SHA256 …` and re-signs the request.
- `signGitHubAppJWT` — recognises `Authorization: Bearer <JWT>` where the JWT is RS256-signed with an integer `iss` claim; re-signs the JWT.

### Pipeline ordering

`ProcessRequest` in [injector.go](/internal/proxy/injector.go) runs:

1. URL literal scan *(existing)*
2. Basic decoder pre-pass *(existing)*
3. **AWS SigV4 signer** *(new)*
4. **GitHub App JWT signer** *(new)*
5. Header literal scan *(existing)*
6. Body literal scan *(existing)*
7. Mismatch detector post-pass *(existing)*

At most one of the new signers can fire per request (each scheme's `Authorization` header form is unique). The literal passes still run afterwards so unrelated placeholders in other headers / body still get swapped.

### Signer return shape

Each signer returns one of three outcomes, emitted as an audit injection with a specific `Location` value:

| Outcome | `Location` | Forwarded? |
|---|---|---|
| Scheme matched, credential matched, signature swapped | `aws_sigv4_resigned` / `github_app_jwt_resigned` | Yes |
| Scheme matched, but no vaulted credential of this scheme covers this host | `scheme_unmediated` | Yes (unchanged) |
| Scheme matched, Veil owns the host for this scheme, but signing could not complete | `signer_failed` (+ `SignerError` field) | **No** — 502 |

Fail-closed path reuses the same return shape as [detectLeak in proxy.go:160](/internal/proxy/proxy.go:160): proxy returns `502 Bad Gateway` with `X-Veil-Error: <reason>` and records the fail-closed audit row before returning. The user-facing body text names the scheme and the failure class.

### "Veil owns the host for this scheme"

Defined as: at least one credential with `Scheme` = the matched scheme has `AllowedHosts` matching the request host (via existing `placeholder.HostMatches`).

### No plugin registry

Signers are called directly by name from `ProcessRequest`. A third signer added later gets one more named call. No dynamic registration, no interface dispatch. Matches how the Basic decoder landed.

### Mismatch-detector interaction

When a signer fires successfully (`Location=…_resigned`), it participates in the injection count the same way Basic decoding does — the detector sees `injectionCount > 0` and does not fire.

When a signer chooses `scheme_unmediated` (no vaulted cred covers this host), injection count is 0. The existing mismatch detector would normally fire on the `Authorization` header shape. That remains correct: if the user has *some* credential for this host but not an AWS/GitHub-App one, and the request carries a signature-based auth header, the detector's warning is still useful signal.

## Vault schema

Extends [record.go](/internal/vault/record.go) with a scheme discriminator and per-scheme typed fields:

```go
type Credential struct {
    // Existing fields unchanged.
    ID                  string    `json:"id"`
    Name                string    `json:"name"`
    Real                string    `json:"real"`          // primary secret (bearer token, basic password, SecretAccessKey, PrivateKey PEM)
    Placeholder         string    `json:"placeholder"`   // primary secret placeholder
    Source              string    `json:"source"`
    AllowedHosts        []string  `json:"allowed_hosts,omitempty"`
    Username            string    `json:"username,omitempty"`             // basic auth
    UsernamePlaceholder string    `json:"username_placeholder,omitempty"` // basic auth
    CreatedAt           time.Time `json:"created_at"`

    // New fields.
    Scheme string `json:"scheme,omitempty"` // "", "basic", "aws", "github_app"

    // aws (SigV4).
    AWSAccessKeyID              string `json:"aws_access_key_id,omitempty"`
    AWSAccessKeyIDPlaceholder   string `json:"aws_access_key_id_placeholder,omitempty"`
    AWSSessionToken             string `json:"aws_session_token,omitempty"`
    AWSSessionTokenPlaceholder  string `json:"aws_session_token_placeholder,omitempty"`

    // github_app.
    GitHubAppID            int64 `json:"github_app_id,omitempty"`
    GitHubInstallationID   int64 `json:"github_installation_id,omitempty"`
}
```

### Primary-secret convention

- `aws`: `Real` = SecretAccessKey, `Placeholder` = secret-key placeholder. (`Scheme = "aws"` = SigV4 signing; a hypothetical future SigV2 would use `aws_sigv2`.)
- `github_app`: `Real` = full PEM-encoded RSA private key (multi-line), `Placeholder` = a *different* PEM-encoded RSA private key (generated fresh at `veil add` time).

### On-disk compatibility

All new fields are `omitempty`. Pre-change vault files load unchanged, re-serialise without new fields. A record with `Scheme` empty is treated as bearer (or basic if `Username != ""`) per existing semantics.

### `Credential.Zero()` additions

Zero additionally clears:
- `AWSAccessKeyID`, `AWSAccessKeyIDPlaceholder`, `AWSSessionToken`, `AWSSessionTokenPlaceholder`
- `Scheme`

GitHub App IDs and installation IDs are not secret and are not cleared. The private-key PEM is already cleared via the existing `Real` / `Placeholder` wipe.

### Scheme detection at runtime

Inferred from fields rather than read from `Scheme` where possible, to keep the type's meaning self-consistent:
- `Scheme == "aws"` iff `AWSAccessKeyID != ""`.
- `Scheme == "github_app"` iff `GitHubAppID != 0`.
- `Scheme == "basic"` iff `Username != ""`.

`Scheme` is still stored for clarity in `veil list` output and for `veil log` filter flags, but signers compare against the typed fields, so a corrupt/mismatched `Scheme` string doesn't cause wrong-signer dispatch.

## Placeholder machinery

### AWS access key ID

The existing `provider_aws.go` generator already produces `AKIA + 16 upper-alphanumeric + sentinel` for access-key-shaped values. Reused as-is.

### AWS session token

Session tokens are long (~400–800 byte) base64-like strings. The placeholder is generated explicitly at `veil add --scheme aws --aws-session-token-*` time via the existing `placeholder.Generate(name+"_SESSION_TOKEN", realValue, existing)` path, using `randBase64ish(len(value))` with sentinel. No new provider-pattern registration is needed — the session token is never auto-detected from an env-key alone; it's always paired with its owning AWS credential at add time.

### AWS secret access key

Existing machinery. No change.

### GitHub App private key (RSA PEM)

New placeholder generator in `internal/placeholder/provider_github.go` (extending the existing GitHub file). Because a PEM-encoded RSA key can't be produced via character-class templating, this generator is a special case:

- Generates a fresh 2048-bit RSA keypair using `crypto/rsa.GenerateKey(rand.Reader, 2048)`.
- Encodes the private key as PKCS#1 PEM (`-----BEGIN RSA PRIVATE KEY-----` … `-----END RSA PRIVATE KEY-----`). PKCS#1 matches GitHub's published App key format; SDKs that want PKCS#8 re-encode on load.
- Returned as the placeholder string. The whole multi-line PEM is what lands in `.env` (quoted if the `.env` writer needs it — see `.env` format note below).
- No sentinel embedded in the PEM body. Identification at the proxy is by JWT `iss` claim, not by byte-pattern match in the wire payload.

Placeholder generation is triggered by a new CLI scheme flag (`--scheme github_app`, see CLI section). The generator is not called via the normal `ProviderPattern` `Match`/`Generate` path because RSA keygen is slow compared to alphanumeric placeholder generation and because no `.env` name alone determines "this is a GitHub App private key."

#### `.env` quoting for multi-line PEM values

`.env` files traditionally hold single-line `KEY=value` pairs. Multi-line values are supported by most `.env` parsers via double-quoted strings with literal `\n` escapes, or via triple-quoted / heredoc syntax depending on parser. Veil's `internal/scanner` must handle both:
- Write multi-line secret values using double-quoted form with `\n` escapes.
- Round-trip on read: preserve the escape form so `syncPlaceholderInEnvFiles` doesn't corrupt existing multi-line values.

Regression test covers: write a GitHub App cred → re-load `.env` → placeholder round-trips byte-identical.

### Sentinel coverage for RSA PEM

`detectLeak` in [proxy.go:262](/internal/proxy/proxy.go:262) scans outbound bytes for `placeholder.Sentinel`. For every other placeholder type, a sentinel is embedded in the placeholder string; `detectLeak` fires fail-closed if any placeholder bytes reach the wire unreplaced.

For GitHub App private keys, no sentinel is embedded, so `detectLeak` cannot fire on a leaked PEM. Accepted limitation:
- The PEM is consumed by the SDK to sign a JWT; the PEM bytes shouldn't appear in any outbound request.
- The JWT-signature-based identification at the proxy is the primary mediation mechanism.
- Documented in `THREAT_MODEL.md` as a scoped gap.

## CLI

Scheme-specific flags added to `veil add`:

```
# Bearer (unchanged)
veil add openai --host api.openai.com --value-stdin < key.txt

# Basic (unchanged)
veil add github-pat --user johndoe --host github.com --value-stdin < pat.txt

# aws (SigV4)
veil add aws-prod --scheme aws --host "*.amazonaws.com" \
    --aws-access-key-id AKIAIOSFODNN7EXAMPLE \
    --value-stdin < secret-key.txt \
    [--aws-session-token-stdin < session-token.txt]

# github_app
veil add gh-app-prod --scheme github_app --host api.github.com \
    --github-app-id 123456 \
    [--github-installation-id 789012] \
    --value-stdin < private-key.pem
```

### New flags

- `--scheme {aws,github_app}` — explicit scheme selector. Omitted = bearer (existing default) unless `--user` is present (= basic).
- `--aws-access-key-id <value>` — AWS access key ID. Required for `--scheme aws`.
- `--aws-session-token-stdin` — read session token from stdin after the secret key (mutually exclusive with reading secret from stdin in the same invocation). If the user needs both from stdin, they invoke separately or use `--aws-session-token-file <path>`.
- `--aws-session-token-file <path>` — read session token from a file. Avoids the stdin-collision with `--value-stdin`.
- `--github-app-id <int>` — GitHub App ID (the integer published on the App's settings page). Required for `--scheme github_app`.
- `--github-installation-id <int>` — optional; stored for tooling convenience. Not used in JWT signing (only in installation-token exchange, which is out of scope).

### Validation

- `--scheme aws` requires `--aws-access-key-id` and the primary-secret input (`--value` / `--value-stdin`) to be present; rejects empty secret.
- Access key ID must match `^AKIA[A-Z0-9]{16}$` (long-lived) or `^ASIA[A-Z0-9]{16}$` (temporary). Otherwise error and point user at STS `--aws-session-token-*`.
- Session token, if provided, must be non-empty base64-ish.
- `--scheme github_app` requires `--github-app-id` > 0 and the primary-secret input.
- PEM content must parse as an RSA private key via `crypto/x509.ParsePKCS1PrivateKey` / `ParsePKCS8PrivateKey`. Error if parse fails — the user fed something that isn't a PEM.
- `--user` mutually exclusive with `--scheme aws` / `--scheme github_app`.

### Output

```
✓ Added aws-prod to vault (aws)
    Access key placeholder:   AKIAVEIL3X9Z2Y1W8VQR
    Secret placeholder:       VeilAWSSecretVEILq3p9f…
    Session token placeholder: VeilAWSSessTokVEIL…
    Hosts: *.amazonaws.com
```

```
✓ Added gh-app-prod to vault (github_app)
    App ID: 123456
    Private key placeholder: <generated RSA PEM — 1,679 bytes>
    Hosts: api.github.com
```

Placeholder strings are printed verbatim for bearer / basic / aws; for github_app the PEM is not dumped to stdout (long and line-wrapped). Instead the CLI writes the placeholder to `.env` directly and prints the `.env` key name.

### `veil list`

Appends a scheme tag next to the credential name:
- `(basic)` — existing.
- `(aws)` — new.
- `(github app)` — new.
- No tag for bearer.

### `veil add --force`

For multi-field credentials, `--force` captures *all* old placeholders and syncs each in `.env` files via the existing `syncPlaceholderInEnvFiles`. Runs one sync pass per placeholder (secret + access-key-id + session-token for AWS; just the PEM for GitHub App).

### `veil remove`

No behaviour change. Existing implementation clears the credential; multi-field placeholders in `.env` are orphaned exactly as today, and the user is told which `.env` entries to delete.

### `veil init` (`.env` auto-detection)

> **Superseded by [`2026-04-23-init-aws-correlation-design.md`](./2026-04-23-init-aws-correlation-design.md)** — init now correlates AWS triples into a single `Scheme: "aws"` credential via strict decoration matching, making the mis-pairing concern below moot. The `mismatch_detector` fallback described elsewhere in this spec remains active for declined prompts, invalid AKID values, and partial groups.

`veil init` continues to scan `.env` files and auto-create bearer-style credentials via the existing provider patterns. It does **not** auto-detect scheme-specific credentials: a `.env` with `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` + `AWS_SESSION_TOKEN` becomes three independent bearer credentials, which will not work for SigV4. The user runs `veil add --scheme aws …` explicitly to get signed auth. (Rationale: auto-pairing heuristically is error-prone — e.g., multiple AWS accounts in one `.env`. An explicit add is cheap and unambiguous. The mismatch detector will surface the "AWS bearer creds don't sign" case, pointing the user at the explicit add.)

## AWS SigV4 signer

**Location:** `internal/proxy/sigv4_signer.go`, invoked from `ProcessRequest` after the Basic decoder pre-pass.

### Detection

Request is SigV4-eligible iff:
- Exactly one `Authorization` header.
- Value starts with `AWS4-HMAC-SHA256 ` (case-sensitive per AWS spec).

Otherwise signer is a no-op for this request.

### Authorization header parse

Extract three comma-separated fields from the value after the scheme:

- `Credential=<AccessKeyID>/<YYYYMMDD>/<region>/<service>/aws4_request`
- `SignedHeaders=<semicolon-separated lowercase header names>`
- `Signature=<hex>`

Parse failure → `signer_failed`, reason `authorization_malformed`.

### Credential lookup

Match AccessKeyID against `AWSAccessKeyIDPlaceholder` across vaulted credentials of scheme `aws` whose `AllowedHosts` covers the request host.

- Match found → continue to re-sign.
- No match AND no AWS credential covers this host → `scheme_unmediated`, forward unchanged.
- No match AND at least one AWS credential covers this host → `signer_failed`, reason `unknown_access_key_id`. Fail-closed.

### Canonical request reconstruction

Follow the AWS Signature Version 4 spec exactly ([AWS docs](https://docs.aws.amazon.com/IAM/UserGuide/create-signed-request.html)). In pseudocode:

```
canonical_request =
    METHOD + "\n" +
    canonicalURI(path)   + "\n" +
    canonicalQueryString(query) + "\n" +
    canonicalHeaders(selectedHeaders) + "\n" +
    signedHeaders + "\n" +
    hex(sha256(body))

string_to_sign =
    "AWS4-HMAC-SHA256\n" +
    x-amz-date + "\n" +
    credentialScope + "\n" +
    hex(sha256(canonical_request))

signing_key =
    hmac(hmac(hmac(hmac("AWS4"+SecretAccessKey, date), region), service), "aws4_request")

new_signature = hex(hmac(signing_key, string_to_sign))
```

Where:
- `METHOD` is the uppercase HTTP method from the request.
- `canonicalURI(path)` and `canonicalQueryString(query)` follow the published normalization rules (URI-encode reserved chars except path-separators; sort query params by name and then value).
- `selectedHeaders` is the set named by `SignedHeaders` — we must use exactly those, in that order, lowercased, with values trimmed of leading/trailing whitespace and inner whitespace collapsed.
- `body` is the body the injector already buffered. (SigV4 without hashed-payload — i.e. `UNSIGNED-PAYLOAD` marker — is rare but supported; detect via the body-hash field of the request, if present as `x-amz-content-sha256: UNSIGNED-PAYLOAD`, skip the body hash and use the marker.)

### Header swaps performed before re-signing

Before computing the new signature, the signer mutates the request headers to carry the *real* identifiers:
- `Authorization` field `Credential=<real-AccessKeyID>/<YYYYMMDD>/<region>/<service>/aws4_request`.
- If the vaulted credential has `AWSSessionToken`, the existing `X-Amz-Security-Token` header (which the SDK inserted with the placeholder token) is replaced with the real session token. If no vaulted session token but the request has one, `signer_failed`, reason `unexpected_session_token`. If vaulted session token but request has none, `signer_failed`, reason `missing_session_token`.

The re-signing then runs over the *mutated* header set, so the new signature matches what goes on the wire.

### Output

- Replaces `Authorization` with the same value but new `Signature=<new-hex>`.
- Replaces `X-Amz-Security-Token` if applicable.
- Emits audit injection with `Location=aws_sigv4_resigned`, `CredentialID`, `CredentialName`. `BytesBefore`/`BytesAfter` record the Authorization header length.

### Known reproduction pitfalls (test vectors required)

- URI path normalization for S3 vs other services (S3 preserves double slashes, others collapse).
- Pre-existing query-string encoding by the SDK vs re-encoding by the signer — we do *not* re-encode the query string; we parse and re-canonicalize.
- Header-value whitespace trimming edge cases.

AWS publishes [test vectors](https://docs.aws.amazon.com/general/latest/gr/sigv4-signed-request-examples.html) that cover the canonical request → string-to-sign → signature pipeline. The signer is tested against the full set in CI before integration tests run.

### Out of scope for the signer

- SigV2.
- Query-string-signed requests (e.g., S3 presigned URLs) — they don't flow through as request auth on the proxy path; the agent generates them and hands them off.
- `AWS4-HMAC-SHA256-PAYLOAD` streaming signatures (used only by S3 chunked uploads; agents that do chunked uploads are a v2 concern).

## GitHub App JWT signer

**Location:** `internal/proxy/github_app_signer.go`, invoked from `ProcessRequest` after the AWS signer (order is commutative but we fix it for determinism).

### Detection

Request is GitHub-App-JWT-eligible iff:
- Exactly one `Authorization` header.
- Value starts with `Bearer ` (case-insensitive per RFC).
- Token portion is a three-segment dot-separated base64url string.
- Header segment decodes to JSON containing `{"alg": "RS256", "typ": "JWT"}` (both fields required).
- Payload segment decodes to JSON containing `iss` as an integer or a string that parses as an integer.

Anything else (e.g., a PAT `ghp_…`, a bearer-shaped API key, an HS256 JWT) is skipped — the literal-matcher pass handles PATs; HS256 is out of scope.

### Credential lookup

Match the parsed `iss` integer against `GitHubAppID` across vaulted credentials of scheme `github_app` whose `AllowedHosts` covers the request host.

- Match found → continue to re-sign.
- No match AND no GitHub App credential covers this host → `scheme_unmediated`, forward unchanged. (The Bearer might still be a PAT for this host; the literal-matcher pass has already run.)
- No match AND at least one GitHub App credential covers this host → `signer_failed`, reason `unknown_github_app_id`. Fail-closed.

### Re-signing

- Reuse the parsed header JSON and payload JSON unchanged. (We do not mutate `iat`/`exp`; the agent set a window, we preserve it.)
- Serialize header JSON → base64url (no padding).
- Serialize payload JSON → base64url (no padding).
- `signing_input = header_b64 + "." + payload_b64`.
- `signature = rsa.SignPKCS1v15(rand.Reader, realPrivateKey, crypto.SHA256, sha256(signing_input))`.
- `new_jwt = signing_input + "." + base64url(signature)`.
- Replace `Authorization` value with `Bearer <new_jwt>`.

The signer does NOT verify the incoming JWT's signature against the placeholder key (we don't need to — the `iss` match is authoritative, and the placeholder private key could have been rotated out). It *does* validate the header's `alg=RS256` / `typ=JWT` invariant so we don't accidentally re-sign something that wasn't actually an RS256 JWT.

### JSON serialization determinism

Go's `encoding/json` does not preserve input field order. To avoid producing a JWT whose payload bytes differ from what the agent emitted (affecting any downstream tool that caches `iss` → JWT mappings), the re-serialized header and payload JSON are produced via a small deterministic encoder that preserves the original key order from the parsed input. Implemented in `internal/proxy/jwt.go`.

### Output

- Replaces `Authorization: Bearer <old-JWT>` with `Bearer <new-JWT>`.
- Emits audit injection with `Location=github_app_jwt_resigned`, `CredentialID`, `CredentialName`. Bytes record the Authorization header length.

### Installation tokens (out of scope, documented behaviour)

After the signer mediates the JWT, the response from `POST /app/installations/<id>/access_tokens` contains an installation token (`{"token": "ghs_…", "expires_at": "…"}`). That token is real, short-lived, issued by GitHub, and is returned through Veil to the agent unmodified. Subsequent agent requests use `Authorization: Bearer ghs_…`, which is a literal bearer token with no Veil mediation — the agent holds the real token for up to an hour until it expires or the agent re-exchanges.

This is explicitly a Class 3 problem and noted in `THREAT_MODEL.md` as a scoped gap.

## Fail-closed integration

`ProcessRequest` returns the injection list (unchanged signature). The proxy front-end (`proxy.go`) already inspects the post-injection wire bytes for sentinel leaks and fails closed via 502 — see [proxy.go:160](/internal/proxy/proxy.go:160). Extend the same mechanism:

```go
if err := firstSignerFailure(injections); err != nil {
    ui.Warnf(os.Stderr, "veil: refusing to forward %s — %s", req.Host, err)
    return req, goproxy.NewResponse(req, goproxy.ContentTypeText, http.StatusBadGateway,
        fmt.Sprintf("veil: signer failed (%s); request blocked (see audit log)", err))
}
```

`firstSignerFailure` returns the first injection with `Location=signer_failed` or nil.

The audit record carries:
- `Location = "signer_failed"`.
- A new `SignerError string` field naming the class (`unknown_access_key_id`, `unknown_github_app_id`, `unexpected_session_token`, `missing_session_token`, `authorization_malformed`, `canonical_request_reconstruction_failed`, `rsa_sign_failed`).

`X-Veil-Error` header on the 502 response carries the same class name for agents that parse it.

## Testing strategy

### Vault schema

- Round-trip a SigV4 credential (access key ID + secret + session token + placeholders) through save → load; values preserved.
- Round-trip a GitHub App credential (App ID + installation ID + PEM + PEM placeholder) through save → load; PEM bytes preserved byte-identical.
- Load a vault file written by the pre-change schema (no `Scheme`, no new fields); existing bearer/basic semantics preserved.
- `Zero()` clears the new AWS fields; does not clear non-secret GitHub App IDs.

### CLI

- `veil add --scheme aws --aws-access-key-id AKIA… --value-stdin` on a fresh vault produces a credential with both placeholders; writes both to `.env` if present.
- Rejects invalid access-key-id format.
- Session token via `--aws-session-token-file` round-trips.
- `veil add --scheme github_app --github-app-id 123456 --value-stdin < key.pem` generates a fresh RSA placeholder PEM; `.env` round-trip preserves multi-line PEM.
- Rejects non-PEM / non-RSA input.
- Rejects `--scheme aws --user …` and other mutually-exclusive combinations.
- `veil list` shows `(aws)` / `(github app)` tags.
- `veil add --force` on multi-field credentials syncs each placeholder in `.env`.

### AWS SigV4 signer (`sigv4_signer_test.go`)

- **AWS published test vectors** — full canonical-request → string-to-sign → signature pipeline verified against every vector at https://docs.aws.amazon.com/general/latest/gr/sigv4-signed-request-examples.html.
- Detection: `AWS4-HMAC-SHA256 …` recognised; other schemes ignored.
- Authorization parse: malformed `Credential=` / missing `Signature=` → `signer_failed` with correct reason.
- Credential lookup: matching placeholder AKIA produces re-sign; unknown AKIA with vaulted AWS cred → `signer_failed`; unknown AKIA without vaulted AWS cred → `scheme_unmediated`.
- Session token round-trip: placeholder `X-Amz-Security-Token` swapped for real; canonical request includes the real token.
- Session-token mismatch cases: vaulted without request → fail-closed; request without vaulted → fail-closed.
- S3 path normalization preserved (double slashes, dots).
- Query-string canonicalization: sorted by name then value; URL-encoded.
- Fail-closed return shape: injection list contains `signer_failed` row with `SignerError`.

### GitHub App JWT signer (`github_app_signer_test.go`)

- Happy path: sign JWT with generated placeholder key, pass through signer, assert new JWT signature verifies with the vaulted *real* key and that header/payload bytes are preserved byte-identical.
- Detection: RS256 JWT with integer `iss` triggers; PAT (`ghp_…`) ignored; HS256 JWT ignored; non-JWT Bearer ignored.
- Credential lookup: matching `iss` → re-sign; unknown `iss` with vaulted app cred → `signer_failed`; unknown `iss` without vaulted app cred → `scheme_unmediated`.
- Key order preservation: parse `{"iss": 1, "iat": 2, "exp": 3}` → re-serialize → bytes equal.
- Malformed JWT (bad base64, non-JSON, missing fields) → signer is a no-op (not `signer_failed`) because it's not "Veil's scheme" — falls through to literal matcher / detector.

### Integration tests (`basic_integration_test.go` extensions)

- **AWS end-to-end**: spin up a local HTTP server that validates SigV4 with a known key; invoke `aws --endpoint-url http://localhost:<port> s3 ls` via `veil run` with `.env` containing both placeholders; assert 200 response and one `aws_sigv4_resigned` audit row.
- **GitHub App end-to-end**: spin up a local HTTP server that validates a JWT signed by a known real RSA key; invoke a curl with a JWT signed with the placeholder key; assert 200 and one `github_app_jwt_resigned` audit row.
- **Fail-closed**: same harness, deliberately corrupt the SigV4 canonical request (e.g., mutate a signed header after parsing) and assert 502 + audit row.

### Out of scope for tests

- Real AWS / real GitHub integration tests (network-dependent, flaky).
- Property-based fuzzing of the signers (valuable but separate workstream).
- Performance / load tests.

## Success criteria

1. `aws s3 ls` through `veil run` with an AWS credential in `.env` succeeds against real AWS; audit shows `aws_sigv4_resigned`.
2. `aws sts get-caller-identity` with a session-tokened credential succeeds.
3. A minimal Octokit or `PyGithub` script that lists App installations through `veil run` succeeds against real `api.github.com`; audit shows `github_app_jwt_resigned` on the `/app/installations/*/access_tokens` call.
4. The mismatch-detector warning seen today for `aws s3 ls` requests no longer fires — `injectionCount > 0` on the `aws_sigv4_resigned` row.
5. A deliberately-corrupted request (e.g., mutated header after signing) is blocked by Veil with a 502 and a `signer_failed` audit row instead of forwarding a bad signature to AWS.
6. `curl https://api.openai.com/…` with a bearer credential is unchanged — no new warnings, no regression.
